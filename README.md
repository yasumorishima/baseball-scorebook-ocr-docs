# Handwritten Scorebook Reader — 手書き野球スコアブック読解 R&D（技術解説）

紙の草野球スコアブックの写真から、打席・走塁データを構造化抽出する研究開発プロジェクトの公開技術解説です。

**本体リポジトリ: [`baseball-scorebook-ocr`](https://github.com/yasumorishima/baseball-scorebook-ocr) 🔒 private** — 記法解読・ソルバー設計・ground truth 転記規約などのノウハウと実データは非公開です（the method is the product）。この repo では公開できる範囲の設計思想・実績・開発プロセスを紹介します。

> **English summary**: Reads handwritten Japanese amateur-baseball scorebooks from photos into structured at-bat data — no paid APIs, no cloud OCR. Deterministic computer vision (OpenCV on a Raspberry Pi 5) fused with a base-running constraint solver that only accepts readings consistent with legal baseball plays. 93% pooled occupancy accuracy on a 31-sheet hand-transcribed ground-truth corpus (the complete archive, now growing live — the latest game was transcribed and verified the day it was played), on a measured-corner pool that keeps widening as previously invisible marks are surgically recovered; 29 consecutive held-out sheets without a single falsification of the frozen constraint model. The main repo is private — this is the public write-up.

## なぜ「未解決領域」なのか

日本の野球スコアブックは独自の記号体系（守備番号の連鎖、塁到達マーク、アウトを表すローマ数字、盗塁・暴投などの機構表記…）を持ち、そこに記録者ごとの手書きの揺れ・省略・書き損じ・シート品質差が重なります。汎用 OCR やマルチモーダル LLM に写真を丸ごと渡しても実用精度は出ません（実測して確認済み）。「どの AI もまだ解けていない」ドメインです。

## アプローチ: 有料 LLM Vision から、無課金 CV + 制約ソルバーへ

初期は LLM Vision に前処理済みクロップを渡す方式を検証しましたが、2026-07 に方針を全面転換し、**API 課金ゼロの決定論的パイプライン**を構築しました。

```
写真 → 格子検出（deskew 込み）→ 手書きインク分離 → テンプレートマッチング（kNN）→ 塁占有制約ソルバー
```

鍵は最後の**制約ソルバー**です。テンプレート認識単体では最難クラスのマークは 4 割程度しか当たりませんが、「野球のルール上、合法な走塁として成立する読みしか受理しない」という制約層を重ねることで、複数の候補読みの中から唯一の整合解を選び出します。曖昧な手書きグリフも、イニングのアウト数・得点・走者の追い越し禁止といった試合の算術が裁定してくれます。

## 実績（2026-08 時点）

- ground truth: **31シート分を全打席レベルで手転記（同一試合の表裏ペアを含む）（過去アーカイブ完結 + 新しい試合を当日取込み中）**（複数の記録者・筆記具・シート品質。促進タイブレークや両面ペア、記録漏れだらけの面などの特殊ケースを含む。最新の試合は**試合当日の夜に転記・検証まで完了**＝パイプラインが「生きた運用」に入った）
- 塁占有の総合精度: **pooled 93%**（テンプレ認識単体 76% → ソルバー統合で +17pt。回収系の改良で計測対象そのものが広がり続けているため、比率より「旧対象を壊さず絶対数を積む」ことを規律にしている）
- 認識層の改良4段（2026-07）: 記法慣習に根ざした距離項の追加、注記の混入を防ぐ**切り出しの多候補化**、字形に重なった別マークを剥がす外科的切り出し、そして**ラベルごとの照合を最近傍1個から上位2個の平均に変更**（外れテンプレ1個でサンプルを奪える構造を解消）で認識段を 41%→**59%** に改善。さらに走塁トレースに溶接されて一度も切り出せていなかった記号の回収で対象自体を広げ、最終段は 80%→**85%**。4段目は全段（認識・制約・結合・最終）が同時に改善したため、以前の『制約ソルバーの組み替えノイズ1振幅ぶんの上振れ＝有望・未証明』とは性質が異なる（修復18/破壊7）
- 認識層の改良5段目（2026-07-26）: 照合の距離そのものを入れ替え、最終段を **85%→88%** に改善（修復13/破壊3、全29試合の実行可能性チェックは維持）。従来は二値画像の重なり率で字形を比べており、数ピクセルのずれで重なりが消えるため「一度だけ太らせてから比べる」という緩和策を挟んでいた。これは *ずれているかどうか* を一つの太さで決め打ちする粗い近似なので、**ずれの実量で距離を測る方式（距離変換）**に置き換えた。既存の緩和策が効いていた事実そのものが、この方向の根拠だった。認識段だけの比較でも 198→209（他条件を完全に固定した対照実験）
- 認識層の改良6段目（2026-07-27）: 距離が **ずれの量は測っていたが向きを測っていなかった**＝どのインクもどのインクに寄れる状態だったので、インクを**ストロークの接線方向で分箱し、同じ向きのお手本にしか距離を課金しない**方式に変更。字形の芯だけでなく、括弧付き数字と裸の記号を分ける**記法の項にも同じ処理**を当てた2段構えで、最終段 **88%→93%**、認識段は **62%→76%**。2段とも認識・制約・結合・最終の全段が同時に改善（修復14/破壊5、修復10/破壊2、全29試合の実行可能性チェックは維持）。**接線を測る範囲の広さ**が実は最も効くパラメータで、実装時に置いたままだった値から狭める方向が正解だった（直感と逆）。なお最終段の +8 のうち 2 程度は調整由来（近傍を1軸ずつ振ると 320±2）で、**頑健なのは認識段の利得**という区別も記録している
- 溶接記号の外科的回収（2026-07 続報）: トレースに完全に溶接された記号は、骨格の through-path を切除した「残り」がグリフか単なるトレースの弧かを**骨格形状ゲート**（長さ・端点数）で判別することで初めて安全に回収できるようになった（無ゲートだと偽発火 44:1 で棄却していた層）。対象 284→287、旧ミスリストは1行も入れ替わらず絶対数 +1
- 溶接記号の回収 続報（2026-07-27）: 上記の外科手術は、記号を横切るトレースの「通り道」を骨格上で探して切除する方式だが、**通り道の両端を「最も離れた2点」として距離だけで選んでおり、その2点が繋がっているかを確かめていなかった**。記号とトレースが別々に枠の縁へ届いている場合、両端が別々の連結成分に選ばれて探索が到達できず、手術ごと中断していた。**同一の連結成分内に限定する**よう直した（旧規則が成功する場合は既に繋がっているので同じ結果になる＝厳密な上位互換）。一度も切り出せていなかった記号を1つ回収し、しかも正しく読めた。計測対象 346→347、**既存コーナーは修復0/破壊0＝1つも壊さずに絶対数 +1**。切り出せない記号は 8→7 に減った
- 到達可能な上限についての注記（2026-07-27）: 残る「切り出せない」記号を1件ずつ調べたところ、**そのうち1つは写真そのものに情報が無い**（該当セルが完全に白飛びしており、閾値をどれだけ下げてもインクが1画素も出ない。同シート130セル中2つだけの孤立した現象）。したがって**この撮影データでの到達可能上限は全件ではなく1件少ない**。残りの未回収は、記号が本来の象限の外に書かれていて「重心でどの角に属するかを決める」現在の規則から漏れる、という別の原因が判明している
- 🔴 **この 93% が前提にしていること（2026-07-28 に明示・自己測定）**: パイプラインは **「どのセルが打席か」「どのコーナーに進塁マークがあるか」「打者がアウトか出塁か」を正解データから受け取った上で**、コーナーの数字を読んでいる。つまり 93% は**「マークの在処を教えてもらった上での読み取り精度」**。前提を明記せずに使わない（**この 3 つは 2026-08-30 に全部 認識器へ置き換わった。下の節を参照**）
- **その前提を2つ外して測り直した（同 2026-07-28）**: 同じ照合機構（字形の向きを課金する距離）を**打球記述の分類**と**マークの有無判定**にも流用して自前で認識させたところ、**出塁/アウトの自前判定で 84%（打席単位）**、**マーク有無は 2445 枠で 94%**。**両方を自前にした状態での最終精度は 299/356 = 84%**（教えてもらった場合の 93% に対して）。⚠️ **この値は当初 297/356 と記録していたが再現しない**（同じコマンドを 2 回走らせて 299・誤り行も同一＝パイプラインは決定的）ので 2026-08-30 に訂正した。残っていた前提「どのセルが打席か」も同日に外した（下の節）
- **設計上の知見2つ**: ①**見落としと誤検出は等価でない**——マークの見落としはその角を永久に読めなくするが、余分な検出はソルバーが「進塁しなかった走者」として処理できる。実測でも**適合率重視の分類器（269）は分類器なし（288）より悪く**、再現率側に振ると 303 まで上がる。⚠️ **ただしこの規則が正しいのは「端」だけだと 2026-08-30 に分かった**（下の節。誤検出を増やし続けると最後は逆に悪化する）。②**一様なノイズで見積もると実際の認識器を過小評価する**——出塁判定は 15.6% 誤るが、損害は一様に 2% 誤らせた場合と同じだった（誤りがソルバーの依存していないセルに集中するため）
- **モデル凍結後に転記した held-out 29枚連続で、制約モデルが一度も反証されていない**（パーフェクト読解のシートも出現）
- 当日取込み（2026-08-30・両面）: 試合当日に両面とも転記して **331/356 = 93%**。この回は**既存の測定対象に対する誤りの集合が凍結時と完全に一致**した（修復も破壊もゼロ）＝取込みが初めて完全に非破壊だった。**構造的な初物が2つ**あり、①写真が規約から90°寝ていた——格子検出は向きを見ていないので**上下逆さまのまま完全に正しい格子を出し、警告も出ない**（既知シートと並べて描画して発見）②打撃面は6イニングあるのにヘッダーの線スコアは5列で止まっていた——先攻が6回表を打った時点でホームがリードしており裏が行われなかったため。**制約チェックもまた効いた**: ある角の数字が紙面上「その打者自身の打順」と読め、そのまま入れると回全体が実行不可能になる。直後の打者が四球で押し出しており、算術的に候補が1つに絞れた


### 「手渡していた事実」を全部なくした（2026-08-30）

上の 3 つの前提のうち最後の 1 つ、**「どのセルが打席か」**を認識器に置き換えました。**これで読み取りに転記データ由来の情報は入っていません**（残るのは「どの列が何回か」「各回の先頭打者はどの行か」という罫線の帳簿だけ）。

| 手渡していた事実 | 総合精度 |
|---|---|
| 3 つとも手渡す | 331/356 = **93%** |
| 3 つとも自前認識 | 298/356 = **84%** |

> 2026-09-03 追記: 罫線の帳簿のうち「各回の先頭打者」も外れ、手渡すのは「どの列が何回か」1 つだけになりました。3 つとも自前認識した数値は **295/356 = 83%**で、手渡し構成の **331 は不変**です（下の節）。

内訳（同じ 31 枚・同じ分母）: 打席セルの判定だけ自前にしても **331 のまま（費用 0）**、出塁/アウトだけなら 323（費用 8）、マーク有無だけなら 311（費用 20）。**3 つの費用を足すと 28 で、全部同時にやると 33**＝認識器は互いに増幅します。**高いのはマーク有無（20）で、精度の見た目が最も悪い出塁/アウト（8）ではありません**。

最後の 1 つは性質が違いました。他の 2 つは「セルが何と言っているか」を変えるだけですが、これは**そもそもどのセルが存在するか**を変えるので、取りこぼすとそのセルの読みが消えるだけでなく、同じ回の他のセルから正解の選択肢まで消えます。検出器はセルごとの残差から 12 個の数値（打席欄のインク量、注記クラスタのインク（総量・最大・個数・角ごと）、走塁トレースの長ストローク、投球カウント帯のマーク数と面積）で判定し、**1 セルではなく 1 シート単位で伏せて**評価しています。**打席 860 のうち 857 を保持（再現率 0.9965）、誤検出 45 / 候補 1800**。

測って分かったことが 2 つあります。

- **動作点は「斜面」ではなく「山」**。取りこぼしを嫌って再現率を上げ続け、最後は全セルを打席と呼ぶところまで振ると、精度は**選んだ点より 12 コーナー悪くなりました**（286）。誤検出は端では無料でも、大量になると高い。上の「再現率側に振る」規則は端でのみ正しい、ということです。
- **「インクがあれば打席」という単純規則を、より低い再現率で上回った**。単純規則は再現率 0.9977（分類器より 1 つ多く拾う）で 290、分類器は再現率 0.9965 で 298。差は全部、誤検出 639→45 のぶんです。分類器が買っているのは「インクはあるが打席ではないセル」（選手交代のジグザグ線と書き込まれた氏名、促進タイブレークの置き走者、暴投の中括弧、取り消し線つきの書き損じ）との区別でした。

うまくいかなかった部分も同じ精度で記録します。この構成で自己整合チェックを走らせると **1 イニングだけ「合法な走塁が存在しない」**と出ます。落とした打席を参照するマークが他のセルにあるためで、**設計が予告していた破局的な失敗が実際に起きた**ということです。点数が下がらなかったのは、その 1 コーナーが元々読み違えていたからで、運であって頑健性ではありません。また**動作点（近傍数と偏り）は 295 を報告するのと同じ 31 枚で選んでいます**＝曲線の形は頑健ですが、山の高さには選択が入っています。


### 立てた仮説が外れ、測り直したら別の犯人が出た（2026-08-31）

上の表で「マーク有無の自前化」が一番高い（20 コーナー）と書きました。その理由として前日に記録した仮説は**「誤検出の切り出しが、照合の物差しそのものを動かしている」**でした（距離の尺度をプール全体の平均から作っているため、答えに使えない誤検出まで尺度に混ざる）。

**測ったら外れでした。** 尺度をラベル付きサンプルだけから作っても、ソルバー非関与の認識段は 1 つも戻りませんでした。

そこで**合計ではなくコーナー 1 つずつを突き合わせる**記録を出せるようにして比べたところ、犯人がはっきりしました。生き残った 351 コーナーを「同じセルに誤検出が増えたか」で二分すると、**セル内の割り当て段の失敗 15 件は全部「誤検出が増えたセル」側に集まり、増えなかった 261 コーナーでは 1 件も壊れていません**。

**つまり誤検出のマークは、そのセルの割り当てに参加して、隣の本物のコーナーを間違った打者に押し付けていた**わけです。いまの探索には「このコーナーは実はマークではない」という選択肢が無く、検出されたら信じるしかありません。

**その選択肢を作って 9 通り 測定しましたが、全部だめでした（同日）。** 基準（選択肢なし）311 に対し、選択肢が実際に使われる設定は例外なく下回り、しかも「使われにくくするほど基準に近づく」という単調な並びになります（0 / 149 / 251 / 292 / 303 / 307、価格を上げきって発火しなくなると 311）。**コーナーを1つ落とすことは値引きだから**です — 探索の目的関数は距離の合計で、落とすと制約が1つ消えるので、本物のコーナーでも「落とした方が安い」。値引きが起きない版（席は残すが「play を指定できないラベルしか取れない」ようにする）でも 306 で、やはりだめでした。

**決着させたのは事前の見積りです。** 探索の時点で使える手掛かりは、誤検出と本物を分けるには弱すぎます（検出器の自信度で約 2:1、ラベルの当てはまりの悪さで約 2.8:1）。取り返せるのは多くて 15 コーナーなのに、巻き添えになりうる本物は 351 個あります。⇒ **直すなら下流ではなく上流＝そもそも誤検出を作らないこと**（同じ取りこぼし率のままで精度を上げる。「再現率を犠牲にして精度を取る」のが有害だという別の実測とは、問いが違います）。

なお尺度の変更自体は、理屈（答えに使えないサンプルが尺度を決めるべきではない）と実績（**修復 3・破壊 0**）で残しました。上の表と数値はこの変更後のものです。誤検出がゼロの構成では旧規則とビット単位で同一なので、過去の測定値は 1 つも動きません。


### 「上流で直す」を測ったら、直すべき対象そのものが入れ替わった（2026-09-02）

前節は「下流の修復は閉じた。誤検出をそもそも作らないこと」で終わっていました。作る前に**まず値段を測りました**。

**天井は +14 でした。** 誤検出を（答えを見て）全部落とす＝この取りこぼし率での完全な検証器は 311→**325**。弧の全額はこれで、残りは検出器が落としている本物のマーク 5 本ぶんです。

**次に、セル自身が証人になる構造条件を 3 つ測りました。** 転記データは明快で、860 打席のうち**アウトのセルが進塁マークを持つ例は 0 件**、到達した塁を超える進塁は 2 件、本塁の進塁マークがあれば必ず得点しています（104/104）。分離も見事で、**誤検出を 51 個落として本物の損失 0**、段階的な到達塁まで使えば **101 個落として損失 2** です。

**それでも 1 点も動きませんでした**（311 / 311 / 309）。理由はコーナー単位の突き合わせが教えてくれました。**壊しているのは「本物のマークと同じセルにいる誤検出」だけ**で（割り当て段の失敗 15/15 がそこ、綺麗なセルの 261 コーナーは 0）、そういうセルの走者は必ず出塁しています。**到達塁を使う条件は、構造上ぜんぶ的外れ**だったわけです。

**手掛かりを 1 つ失いました。** いちばん強い物証に見えたのは走者自身の走路です（照合に使う切り出しは長いストロークを構成上落とすので、認識器からは見えない）。ところが「2 塁に到達」と転記されたコーナーで走路が検出されるのは **4.8%** だけ。器械が悪いのか手掛かりが無いのかを切り分けるため、絶対距離を使わない測り方（ダイヤの中心まわりに角度でインクを刻む）に替えると、**到達した塁でぴたりと止まる単調な掃引**が出ました——**が、検出済みの文字の箱を消すと消えました**。あの信号は**コーナーの数字が自分自身を保証していただけ**です。現物を見て決着しました：**この記録者は塁の走路を一切描いていません**。得点の丸の検出器も同じ形で較正し直しています（現行は再現率 0.64・誤検知 197＝**探す窓が固定で、丸が窓より大きいと「穴が無い」と読む**＝証拠が大きいほど器械が小さくなる）。

**誤検出の正体を並べて読みました。** 本物と同じセルにいる 79 個を一覧にすると、**PB・S・WP・1E/2E/3E・DB・T.O**、そして括弧やストロークの断片でした。**大半は誤検出ですらありません**——記録者が実際に書いたマークで、**打者番号を持たない進塁**だから転記では注記欄に回っているだけです。いまの探索は「番号つきの到達」としてしか読めないので、セル内の単調な鎖が**隣の本物を次の打者に押し付ける**。実際、教えてもらった場合に正解で自前だと不正解になる 17 コーナーのうち **11 が「番号なしのトークンが上段にいて、本塁のマークが 1 打者ぶん後ろにずれる」**でした。

**決定的だったのは、消すことと同値な操作が見つかったことです。** 番号なしのコーナーを**削除せず、「play を指定できないラベル」に強制**する（席も費用も残し、打者を指定する力だけ失わせる）と、**325 で、削除した場合と完全に同じ**でした。⇒ **足りないのは検証器ではなく語彙**。削除は間違えると本物のマークを丸ごと失いますが、ラベルなら間違えても失うのは「指定する力」だけで、下流の占有ソルバーが拾い直せます。

### その語彙を作る 4 経路も、全部だめだった（同日）

強制が効くのは確定しているので、あとは**どのコーナーが番号なしかを当てる**だけです。4 通り測って全部 null でした。

1. **既存の照合距離に「番号なし」クラスを足す**: 発火はしますが**本物を 70/351 吸い込んで 262**。原因は形ではなく**クラスの大きさ**で、数字は 1 打者番号あたり十数枚のテンプレなのに、番号なしは 178 枚を 1 クラスに抱えるため、2 近傍平均がほぼ何にでも近くなります。差を要求すると基準へ**単調に戻るだけ**（289 / 299 / 309 / 311）で、一度も超えません。
2. **別の特徴で専用の認識器を作る**（成分数・穴・列の切れ目・左右端でインクがどれだけ高く立つか・縦横比・密度・大きさ・位置）: **シート単位で伏せた評価**で、受理 14 に対し巻き添え 1＝**14:1** と、必要な交換比（およそ 4:1）を大きく上回りました。**それでも通しでは 310 / 310 / 304**（基準 311）。理由は測れば明快で、**自信のあるトークンは無害なトークン**です——受理した 14 のうち本物と同じセルにいるのは 2 つだけで、単独のトークンは誰も取り合っていない打者を指定するので 0 円。
3. **セル内で同じ打者番号を共有させる**（1 打席で 2 つ進む走者がいるので、いまの「厳密に増加」が真を棄却しているのでは）: 転記データが否定しました。**番号つき進塁を 2 つ以上持つ 84 セルで、番号の重複は 0 件**。制約は健全です。
4. **解が無いときだけ修復する**（静的な門は必ず値引きになるが、実行不能時だけなら値引きではない）: **一度も発火しません**。実行不能なイニングは 3 構成すべてで **0 件**でした。誤検出はイニングを不能にするのではなく、**最安の実行可能解を間違ったものにする**のです。

**この日いちばん一般的な発見**は 3 度出た同じ形です：**この故障モードでは「自信」と「damage」が逆相関する**。到達塁の条件（51:0）も得点の条件（52:0）も形状認識器（14:1）も、**分離は絶好調なのに 1 点も動かない**。効くのは「番号つきに見えて、本物の隣にいるトークン」だけで、それは定義上どの自信度でも分けられません。

**次に狙うのはここではありません。** 転記データ由来で残っているのは罫線の帳簿 2 つ（どの列が何回か・各回の先頭打者はどの行か）だけで、**後者を置き換える構造は測ってあります**——1 イニングの打席は打順の**連続区間**（174 回中 172）、次の回の先頭は前の回の最後の次（143 中 138）。連続性を構成上強制する復号にすれば、帳簿を 1 つ外しつつ誤検出も構成的に減ります（⚠️ 174 分の 2 を棄却するので**硬い制約にはできない**＝費用つきの選好として入れます）。


### leadoff の台帳を「削除して」値段を測り、そのうえで外した（2026-09-03）

紙から読まずに転記から受け取っていた事実は、罫線の帳簿 2 つだけになっていました。そのうち「各回の先頭打者はどの行か」を外しました。

**値段は議論ではなく削除で測りました。** 置き換えるのは台帳が符号化している構造そのものです＝1 イニングの打者は打順の連続区間なので、先頭打者は前の回の最後の打者の次であり、シートの最初の回は 1 番から始まる。作る前に転記データで測ると、**前の回を持つ 174 回のうち 143/143 で台帳と同じ並び**、**31 枚すべてが 1 番始まり**でした。

**測る量は「先頭打者の番号」ではなく「並び順」です。** 短い回は複数の先頭候補が同じ並びを作りますし（同値な候補の数は 1 個から 9 個まで分布します）、ソルバーが食うのは並びだけです。番号で測ると 143 中 138 に見え、**存在しない 5 件の失敗を探すことになります**（前回の記録はそう書いていたので取り下げました）。

| 打席セルの与え方 | 台帳あり | 連鎖のみ | 連鎖＋連続性（現在の既定） |
| --- | --- | --- | --- |
| 転記から手渡す | 331 | 331 | **331**（実行可能性チェック合格） |
| 自前認識 | 331 | 323 | **328** |
| 3 つとも自前認識 | 298 | 290 | **295** |

つまり**手渡し構成では台帳の値段はゼロ**なので、既定を切り替えました。**93% の見出しは動かないまま、手渡す事実が 1 つ減りました**。台帳が買っていたのは全部、打席検出器の誤検出 45・取りこぼし 3 が連鎖を後続の回へずらすことへの保険です。

**実行可能性チェックが本物のバグを 1 つ捕まえました。** 連続性の判定には打線の人数が要り、9 人・10 人・11 人のシートが実在します（31 枚で 12・18・1）。誤検出が人数を水増ししないようにと「2 回以上打席に立った最も深い打順」を使ったところ、**10 番が本当に、ただし 1 打席だけ立つシートを 9 人と読み**、その回はどの先頭候補とも整合しなくなって誤った人数での連鎖に落ち、**転記データ自身のマークが実行不可能**になりました。単純に「使われている最も深い打順」が、手渡し構成では構成上つねに正しい値です。

### 残る 3 コーナーは 4 経路とも取れなかった（同日）

1. **費用つきの (開始, 長さ) 復号**——前回の記録が名指ししていた形です。並び一致は **164/174** で素朴な連続性規則の 165 に届かず、3 つの価格を振っても 159〜164 で平坦でした。
2. **「1 イニングのアウトは 3 つまで」で誤検出を反証する**——転記データ 174 回の最大がちょうど 3 なので、**真を 1 件も棄却しない健全な制約**です。ところが**予測値では 68 回が 4 つ以上を示し、そのうち 43 回は誤検出を 1 つも含みません**。壊しているのは打席検出ではなく出塁/アウトの認識器でした。
3. **決めずにソルバーへ候補リストを渡す**——2 つの手掛かりが出す並びを全部価格付けして最安を採ります。リストは台帳の並びを **172/174** で含み、選択が実際に生じるのは 20 回だけ。**コストが代替を選んだのは 0 回**で、決定的なのは**台帳の並びを外から強制しても同点**だったことです。残差は選択の問題ではありません。
4. **検出器自身の確信度に誤検出を指させる**——誤検出はその回でいちばん弱いセルであることが **45 件中 30 件**。ただし一意な候補が無いときだけ弱い 1 本を投票から外す規則は 9 回発火して、買えるのは 1 回ぶんでした。

4 つが同じ場所に着地する理由は、1 か月前にマーク検出器で出たのと同じ法則の別設定です：**壊す誤検出は、構造を「より」整合的に見せる方**。コーナーを失う 6 回は誤検出のせいで**誤った先頭候補が一意に見える**回で、不整合を手掛かりにする規則は原理的に届かず、一意な候補を疑えば正しい 169 回を失います。

## 独立データとの相互検証（2026-07）

チームサイトに手入力されていた試合別成績（別の人手・別の情報源）と、GT 由来の選手別成績を9試合ぶん突合しました。**7/9 試合でスコアが完全一致、選手単位でも大部分のスロットが桁単位で一致**（単打+三塁打+本塁打+四球+打点5 という行まで一致）。さらに GT 側で「判読曖昧」とフラグしていたグリフ5つが、シート自身の集計行とサイトデータの両方から同じ向きに確定しました。逆にサイト側の入力ミス候補（スコアの1点違い・交代選手の打席二重計上・死球の記録漏れなど）も特定でき、**相互検証が双方向に機能する**ことを確認しています。残っていた食い違い2試合も原本の再精査で決着し（うち1試合は転記時に見落としていたシート自身のラインスコアが裁定者になり、GT 側を訂正）、紙で答えられる疑問は全てクローズしました。

## 開発プロセスの規律

- **frozen model + held-out 評価**: 認識モデルは凍結し、新しく転記するシートはまず「答えを見せない汎化テスト」として評価してからテンプレートに取り込む
- **honesty ledger**: テンプレート追加のたびに「直った旧ミス」と「新たに壊れたセル」を両方記録する（テンプレ増は非単調に効く。良い話だけを書かない）
- **敵対的レビュー**: 転記データは毎回 LLM による整合レビューにかけ、走塁の合法性・得点の算術を突合する（実際に人間の転記バグを検出した実績あり）。ただし認識パイプライン自体に生成 AI は使わない
- **個人情報の分離**: 選手名は転記データに含めず、スコアブック画像・実試合データはリポジトリ外で管理する
